End-to-End VDI Onboarding Pipeline

From three disconnected systems and 2 hours of daily Excel work to a single 10-minute reproducible run with anomaly detection — now operated by a teammate via SOP.

Python pandas BeautifulSoup PowerShell Active Directory SOP
~250 workers onboarded / month
2 h → <10 min daily processing time
1 year history in one tracker
SOP-driven operated by a teammate

Problem: Onboarding contractor VDI access required reconciling data across three systems — an ITSM ticket export (metadata buried in HTML cells), an identity-management warehouse, and a year-long historical tracker. The manual Excel reconciliation took up to two hours every day; missed AD group assignments re-opened as analyst tickets downstream.

Solution — a four-stage pipeline:

  1. Parse — a Python script extracts ~10 structured fields per worker from the ITSM export’s HTML cells (name, manager, region, access pool, start date, rehire flag, contact email).
  2. Reconcile — cross-references parsed records against the identity-management export to attach assigned usernames, with name normalisation handling casing, middle initials, and preferred-name variants.
  3. Anomaly detection — checks each (pool, region) combination against the rolling 12-month history. Combinations seen in the past 6 months auto-populate the correct security group; unseen combinations are flagged for manual review (most likely a new pool, or one that’s been retired).
  4. Provision & verify — PowerShell + ActiveDirectory module bulk-adds users to their security groups, then immediately re-reads membership to surface any mismatches before the batch closes.
View anomaly-detection logic (pool history lookup) 
def flag_new_pool_combinations(records, history, window_days=180):
    """For each record, check whether its (pool, region) combination
    has been used in the rolling history window.

      • Seen recently     -> auto-populate the historical security group.
      • Not seen recently -> flag for manual review (new or retired pool).
    """
    cutoff = datetime.now() - timedelta(days=window_days)
    history["seen_at"] = pd.to_datetime(history["seen_at"])
    recent = history[history["seen_at"] >= cutoff]

    # Lookup: (pool, region) -> most recent security group seen in window
    lookup = (
        recent.sort_values("seen_at", ascending=False)
              .drop_duplicates(subset=["pool_name", "region"])
              .set_index(["pool_name", "region"])["security_group"]
              .to_dict()
    )

    def resolve(row):
        return lookup.get((row["pool_name"], row["region"]))

    records["security_group"]      = records.apply(resolve, axis=1)
    records["needs_manual_review"] = records["security_group"].isna()
    return records

Outcomes

  • Daily processing reduced from ~2 hours to under 10 minutes, including AD remote-desktop launch and verification checks.
  • One year of onboarding history consolidated into a single searchable tracker.
  • Group-assignment errors caught at the source rather than as downstream re-opened tickets.
  • Now run by a teammate following the SOP — the automation belongs to the team, not just me.

Laptop Lifecycle: Refresh & Decommissioning

Technical Writing Hardware Asset Management BitLocker NIST 800-88 ServiceNow

Context: Internal knowledge base article covering both ends of the corporate laptop lifecycle — fresh imaging when a device is deployed or refreshed, and secure decommissioning when a device leaves the fleet. Written for IT Support Specialists handling on-site requests. Authored on Confluence; reproduced here in simplified form.

Read article
Author: Olena Karpenko Last updated: May 2026 Category: Hardware · Asset Lifecycle · Imaging

Overview

This article documents the full corporate-laptop lifecycle from the IT Support perspective: deploying a freshly imaged device to a user, and securely retiring a device when it leaves the fleet. The two workflows share the same asset-management discipline — every state change must be reflected in the ServiceNow CI record.

Prerequisites

  • Access to ServiceNow asset records and the CI database
  • PXE boot server or USB imaging stick with the current standard image
  • WinPE recovery environment for secure erase
  • BitLocker recovery-key access via the central key escrow
  • Documented asset disposal route for your region (vendor return / e-waste / refurbish)

Part 1 — Refresh

Pre-imaging Checklist

  1. Verify the device exists in the asset tracker — serial number must match the ServiceNow CI record.
  2. Wipe existing data: boot to WinPE and run secure erase. For BitLocker-encrypted drives, confirm the recovery key has been escrowed before wiping.
  3. Check BIOS: Secure Boot enabled, TPM 2.0 active, boot order set to network first for PXE.

Imaging

  1. Boot to PXE or USB imaging stick and select the correct image for the device model and region (e.g. EMEA standard image).
  2. Let imaging complete without interruption — typical time 20–40 min depending on drive speed.
  3. On first boot: join domain, apply GPO, confirm Windows Update resolves to the current patch level.

Post-imaging Checklist

  • Asset tag confirmed in the ServiceNow CI record
  • Device joined to domain and in correct OU
  • User account logs in successfully, MFA enrolled
  • Core apps present: Teams, Outlook, Chrome, VPN client
  • BitLocker enabled and recovery key escrowed
  • Ticket updated with imaging date and build version

Part 2 — Decommissioning

Pre-decommission Checklist

  1. Confirm the decommission request in ServiceNow — verify the requester is an authorised manager or HR contact.
  2. Coordinate with the user on device collection and confirm whether any local data needs to be migrated.
  3. Validate that the asset record matches the physical device — serial number, model, and current owner.
  4. Note any peripherals returned with the device (docks, monitors, adapters); record separately as they have their own lifecycle.

Data Destruction

  1. Boot to WinPE; pull and escrow the BitLocker recovery key if not already on file.
  2. Run a NIST 800-88 compliant secure erase (single-pass cryptographic erase for SSDs; multi-pass overwrite for legacy HDDs going to e-waste).
  3. Verify post-wipe with a test boot — the drive should fail to boot, confirming the operating system is gone.
  4. Capture the wipe-completion screen as evidence and attach it to the decommission ticket.

Critical: Never wipe a BitLocker-encrypted drive whose recovery key has not been escrowed. Doing so destroys any possibility of recovering data if it turns out to be needed for legal hold or user request.

Hardware Inspection

  1. Visual check — screen, keyboard, ports, hinges, chassis.
  2. Functional check — power, charging, USB ports, webcam, speakers.
  3. Categorise outcome:
    • Refurbish-ready — good condition, can re-enter the fleet
    • Vendor return — out-of-warranty resale or leasing return
    • E-waste — irreparable damage; route to certified disposal

Asset Retirement

  1. Update the ServiceNow CI status to Retired or Disposed.
  2. Detach the device from the current owner; archive the assignment history.
  3. Log the disposal route taken and any vendor / e-waste reference number.
  4. If the device leaves the premises, capture handover signature or shipping label number on the ticket.

Verification Checklist

  • BitLocker recovery key escrowed and matched to the serial number
  • Wipe-completion evidence attached to the ticket
  • ServiceNow CI status updated to retired / disposed
  • Owner detached and assignment history archived
  • Disposal route documented with reference number
  • Peripherals processed separately or returned to inventory

Troubleshooting

  • BitLocker key not escrowed — do not wipe. Escalate via the recovery-key team; wiping an unescrowed device loses any chance of data recovery.
  • Serial mismatch with CI record — investigate before proceeding. The device may have been swapped without record update; correct the CI first.
  • Wipe hangs indefinitely — common on failing drives. Note the drive serial separately for vendor RMA and use a physical destruction route (shredder / degausser) instead of software erase.
